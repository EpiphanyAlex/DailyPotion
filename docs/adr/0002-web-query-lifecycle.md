# ADR-0002：Web 查询、失效与认证作用域

状态：accepted；实现：Phase 2 查询/写入和数据库 RLS 已存在，页面缓存与失效待 Phase 4–8 接入。

## 背景

Supabase 是权威事实源；Web 页面可能同时遇到写入、切换配方、退出登录和账号切换。持久化私人响应会让旧账号或旧请求污染新视图。

## 决定

- 当前查询层不保存模块级或跨会话缓存。公开配方可以按 [总览 §5](../prd/00-overview.md) 静态生成/ISR；私人数据按请求身份读取，不放入共享 Next.js 缓存，也不放 localStorage。
- 接入页面时，如引入客户端查询库，缓存只存可由 Supabase 重取的投影。私人 key 必须含用户 ID；配方详情 key 含 slug，筛选视图以 URL 参数为身份。服务端缓存公开内容与私人投影分开。登录、登出、账号变化时清除全部私人投影与乐观状态，重新取当前用户数据；RLS 仍负责授权。
- 写入前对同一资源的重复点击做 single-flight/禁用控制。乐观展示须保留旧快照。写入失败回滚快照、展示错误且允许重试；写入成功使相关权威查询失效并重取：酒瓶变更影响酒柜与所有库存匹配视图，收藏影响配方卡/详情/收藏页，评分影响个人评分，调酒记录影响 History。重取失败只提供“重试读取”，不得再次发送已成功的写入。
- 迟到响应须用请求取消或身份/序号校验丢弃。旧 slug 的响应不能进入新详情；旧账号的响应不能进入新会话。新鲜度应基于页面访问和明确失效，不采用桌面 IPC 的永久缓存策略。允许浏览器离线/短暂错误时展示明确的旧数据状态，但不把它当权威成功状态。

## 后果与落地

现有 `scripts/verify-queries.ts` 已以两个真实账号验证查询层与 RLS 隔离。Phase 4 认证接入时验证浏览器账号切换与私人状态清理；Phase 5 酒柜、Phase 6 配方页、Phase 7 收藏/记录、Phase 8 首页各自落实定向失效和 [交互验收](../engineering/interaction-acceptance.md)。具体交互仍以各 [feature PRD](../prd/README.md) 为准；本 ADR 不要求现在新增缓存依赖或空的组件测试。
